# Technical spec: мультиязычность

## 1. Назначение документа

Этот документ описывает техническую схему мультиязычности первой версии сайта Крим.

Сайт должен поддерживать две языковые версии: украинскую по умолчанию и русскую как вторую версию. Мультиязычность должна работать для публичных страниц, объектов, статусов, кнопок, контактных действий, подписей, SEO-данных и системных сообщений.

Документ не описывает точный визуальный вид переключателя языка, дизайн страниц или тексты переводов. Эти темы относятся к visual rules / skills и контенту.

## 2. Языки первой версии

В первой версии поддерживаются только два языка:

- украинский;
- русский.

Украинский язык является языком по умолчанию.

Русский язык доступен как вторая языковая версия.

Другие языки, автоматический перевод и определение языка по геолокации не входят в первую версию.

## 3. URL-структура языков

Рекомендуемая схема языковых URL:

```txt
/              украинская главная страница
/projects      украинский список объектов
/contacts      украинские контакты

/ru            русская главная страница
/ru/projects   русский список объектов
/ru/contacts   русские контакты
```

Украинская версия не должна требовать префикс `/uk`, если не будет отдельно принято другое решение перед реализацией.

Русская версия должна использовать префикс `/ru`.

Эта схема должна быть согласована с technical spec по маршрутам и SEO.

## 4. Хранение списка языков

Список поддерживаемых языков должен храниться в одном понятном месте.

Например, в `src/i18n` можно предусмотреть:

```txt
src/i18n/
  config.ts
  dictionaries/
```

В конфигурации нужно зафиксировать:

- поддерживаемые языки;
- язык по умолчанию;
- URL-префикс для русского языка;
- отсутствие URL-префикса для украинского языка;
- человекочитаемые названия языков для переключателя.

Точный формат файла должен быть выбран на этапе реализации.

## 5. Интерфейсные тексты

Короткие интерфейсные тексты должны храниться в словарях.

К таким текстам относятся:

- названия пунктов навигации;
- кнопки;
- подписи контактных действий;
- статусы объектов;
- системные сообщения;
- подписи к характеристикам;
- короткие тексты ошибок;
- подписи переключателя языка.

Пример структуры:

```txt
src/i18n/dictionaries/
  uk.ts
  ru.ts
```

Словари должны иметь одинаковую структуру для украинского и русского языка, чтобы отсутствующий перевод было легче заметить до публикации.

## 6. Контент объектов

Контент объектов должен поддерживать две языковые версии.

Для каждого объекта нужно предусмотреть переводимые поля:

- название, если оно отличается по языкам;
- краткое описание;
- подробное описание;
- основные преимущества;
- пояснение стадии строительства;
- подписи к медиа, если они используются;
- SEO title;
- SEO description.

Непереводимые или общие поля не должны дублироваться без необходимости.

К общим полям относятся:

- идентификатор;
- slug;
- статус как техническое значение;
- цена в USD;
- площадь;
- количество комнат;
- количество санузлов;
- ссылки на фото и видео;
- порядок медиа;
- признаки публикации.

## 7. Статусы объектов

Статусы объектов должны храниться как технические значения:

- `building`;
- `available`;
- `sold`.

Пользователю они должны отображаться на выбранном языке.

Соответствие должно быть задано в словарях:

- украинские варианты для украинской версии;
- русские варианты для русской версии.

Статус не должен храниться в данных объекта как произвольный текст на одном языке.

## 8. Контакты и мессенджеры

Контактные данные не должны дублироваться по языкам без необходимости.

Общими для языков должны быть:

- номер телефона;
- ссылка для звонка;
- ссылка WhatsApp;
- ссылка Viber.

Переводимыми должны быть:

- подписи к телефону;
- подписи к WhatsApp и Viber;
- поясняющие тексты;
- тексты действий.

Email не входит в каналы связи первой версии.

## 9. Фото и видео

Фото и видео сами по себе не переводятся.

Переводимыми могут быть:

- подписи к фото;
- подписи к видео;
- описание этапа строительства;
- пояснения к материалам «до и после».

Если медиа не имеет подписи, отсутствие подписи не должно ломать языковую версию страницы.

Медиа-ссылки должны быть общими для украинской и русской версий, если нет отдельной причины использовать разные файлы.

## 10. Отзывы и доверительные материалы

Отзывы нужно обрабатывать осторожно.

Если отзыв изначально написан на одном языке, до реализации публичного отображения нужно решить:

- показывать отзыв в оригинале;
- показывать перевод;
- показывать оригинал и перевод;
- не показывать отзыв, если нет разрешения или понятного перевода.

Временные отзывы могут использоваться только как заглушки на этапе разработки и не должны публиковаться как реальные отзывы клиентов.

Доверительные тексты, написанные компанией, должны быть подготовлены на украинском и русском языках.

## 11. Переключение языка

Пользователь должен иметь возможность переключить язык сайта.

Технически переключение языка должно:

- переводить пользователя на соответствующую языковую версию текущей страницы, если она существует;
- сохранять объект при переключении языка, если пользователь находится на странице объекта;
- не отправлять пользователя всегда на главную страницу без необходимости;
- показывать понятное поведение, если соответствующая страница временно недоступна.

Пример:

```txt
/projects/house-kyiv-01
/ru/projects/house-kyiv-01
```

Точный внешний вид переключателя языка относится к visual rules / skills.

## 12. Поведение при неполном переводе

Перед публикацией сайта основные тексты должны быть подготовлены на украинском и русском языках.

Если отдельный перевод временно отсутствует на этапе разработки:

- страница не должна ломаться;
- отсутствие перевода должно быть заметно разработчику;
- нельзя публиковать страницу со случайной смесью языков в одном интерфейсе;
- fallback на украинский допустим только как временная мера разработки, а не как нормальное публичное поведение.

Для первой публичной версии нужно стремиться к полным переводам основных страниц и объектов.

## 13. SEO для языковых версий

SEO-данные должны быть подготовлены отдельно для украинской и русской версий.

Для каждой языковой версии нужно предусмотреть:

- `title`;
- `description`;
- основной заголовок;
- Open Graph title;
- Open Graph description;
- корректный URL;
- язык страницы.

Если будет использоваться `hreflang`, он должен связывать украинскую и русскую версии одной и той же страницы.

Точная реализация SEO должна быть согласована с technical spec по маршрутам и SEO.

## 14. Системные сообщения

Системные сообщения должны поддерживать выбранный язык.

К таким сообщениям относятся:

- страница не найдена;
- объект не найден;
- нет доступных объектов;
- нет видео или фото, если такое сообщение используется;
- ошибка перехода или недоступный раздел, если такое сообщение потребуется.

Системные сообщения должны быть короткими, понятными и не смешивать языки.

## 15. Проверка перед публикацией

Перед публикацией сайта нужно проверить:

- украинская версия открывается по маршрутам без `/uk`;
- русская версия открывается через `/ru`;
- переключатель языка ведет на соответствующие страницы;
- объекты доступны на двух языках;
- статусы объектов переведены;
- кнопки и контактные действия переведены;
- SEO-данные подготовлены на двух языках;
- временные или непереведенные тексты не попали в публичную версию;
- нет случайного смешения украинского и русского в одном интерфейсе.

Техническая проверка может быть усилена типами, тестами или скриптами на этапе разработки.

## 16. Что не входит в первую версию

В первую версию мультиязычности не входят:

- больше двух языков;
- автоматический машинный перевод;
- определение языка по геолокации;
- отдельные контакты для разных языков;
- отдельные цены для разных языков;
- отдельные валюты для разных языков;
- сложная система управления переводами через админку;
- Supabase для управления переводами;
- пользовательское сохранение языковых предпочтений в личном кабинете.

Эти возможности могут быть добавлены позже только через отдельные спецификации.

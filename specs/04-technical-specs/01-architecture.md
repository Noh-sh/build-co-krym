# Technical spec: общая архитектура первой версии

## 1. Назначение документа

Этот документ описывает общую техническую архитектуру первой версии сайта Крим.

Архитектура должна поддерживать уже утвержденные спецификации: публичный сайт строительной компании, страницы объектов, фото и видео, контакты, мультиязычность, отображение цены в USD и базовую SEO-подготовку.

Документ не описывает точную структуру папок, конкретные компоненты интерфейса, визуальный стиль, базу данных, API или административную панель. Эти детали должны быть описаны в отдельных technical specs.

## 2. Общий подход первой версии

Первая версия сайта должна быть публичным frontend-проектом на Next.js.

Основной подход:

- сайт работает как публичная витрина компании;
- страницы доступны без авторизации;
- контент заранее подготовлен и хранится в проекте;
- объекты, тексты, цены, контакты, фото и видео добавляются вручную через файлы проекта;
- административная панель и Supabase не входят в первую версию;
- формы сбора личной информации не используются;
- обращения идут через телефон, WhatsApp и Viber.

Такой подход подходит для первой версии, потому что компания небольшая, строит примерно до пяти домов в год, а объем контента на старте можно поддерживать вручную без отдельной системы управления.

## 3. Основные технические части сайта

Первая версия должна состоять из следующих технических частей:

- публичные страницы сайта;
- данные объектов и текстов;
- медиа-файлы: фотографии и загружаемые короткие видео;
- маршруты для главной страницы, списка объектов, страниц объектов, контактов и других публичных разделов;
- поддержка украинской и русской языковых версий;
- базовая SEO-подготовка;
- ссылки для звонка, WhatsApp и Viber.

Каждая часть должна быть устроена так, чтобы сайт можно было развивать дальше без полной переделки первой версии.

## 4. Next.js как основа проекта

Next.js используется как основа первой версии сайта.

На уровне архитектуры Next.js должен обеспечить:

- маршрутизацию публичных страниц;
- генерацию страниц объектов;
- подготовку метаданных для SEO;
- работу с изображениями;
- разделение страниц и переиспользуемых компонентов;
- возможность дальнейшего расширения проекта.

Точный выбор App Router или другой внутренней структуры Next.js должен быть описан в technical spec по структуре проекта.

## 5. Контент без базы данных

В первой версии контент не должен зависеть от базы данных.

Данные сайта должны храниться в проекте в виде подготовленных файлов. К таким данным относятся:

- объекты и их характеристики;
- статусы объектов;
- цены в USD;
- тексты страниц;
- контактные данные;
- ссылки на фото и видео;
- тексты для украинской и русской версий;
- реальные отзывы, если они доступны.

Ручное хранение контента в проекте допустимо для первой версии, потому что объектов мало, а админка пока не входит в обязательный объем.

Формат хранения данных должен быть описан отдельно в technical spec по контенту и данным.

## 6. Медиа первой версии

Фото и видео должны использоваться как реальные материалы компании.

На уровне архитектуры нужно предусмотреть:

- хранение фотографий в проекте или в выбранном публичном хранилище, если это будет отдельно утверждено;
- хранение загружаемых коротких видео в проекте или в выбранном публичном хранилище, если это будет отдельно утверждено;
- связь медиа с конкретными объектами;
- возможность показывать медиа на главной странице, в списке объектов, на странице объекта и в доверительных блоках;
- работу страниц даже при неполном наборе медиа.

Первая версия не должна зависеть от YouTube, Instagram или TikTok как основного источника видео.

Подробные правила по форматам, размерам, оптимизации и размещению медиа должны быть описаны в отдельном technical spec по фото и видео.

## 7. Мультиязычность

Сайт должен поддерживать две языковые версии:

- украинский язык по умолчанию;
- русский язык как второй вариант.

На уровне архитектуры нужно предусмотреть:

- отдельные тексты для украинской и русской версий;
- переключение языка пользователем;
- корректные маршруты или параметры языка;
- перевод статусов объектов, кнопок, подписей и системных сообщений;
- возможность подготовить SEO-метаданные для каждой языковой версии.

Точная техническая схема маршрутов и хранения переводов должна быть описана в отдельном technical spec по мультиязычности.

## 8. Контакты и обращения

Первая версия не должна собирать заявки через форму.

Архитектура должна поддерживать быстрые переходы:

- звонок по номеру телефона;
- переход в WhatsApp;
- переход в Viber.

Контактные данные должны храниться как часть подготовленного контента проекта. Если номер телефона или ссылки мессенджеров изменятся, это должно исправляться в данных проекта без изменения логики страниц.

Интеграция с CRM, сохранение обращений, уведомления и Supabase для обращений не входят в первую версию.

## 9. SEO и публичная доступность

Сайт должен быть подготовлен к базовой поисковой оптимизации.

На уровне архитектуры нужно предусмотреть:

- понятные публичные URL;
- отдельные страницы для объектов;
- корректные заголовки страниц;
- мета-описания;
- индексируемый текстовый контент;
- корректную работу украинской и русской версий;
- возможность подготовки Open Graph данных для отображения ссылок в мессенджерах и социальных сетях.

Подробная структура маршрутов, URL и SEO-правил должна быть описана в отдельном technical spec по маршрутам и SEO.

## 10. Mobile-first технический подход

Сайт должен проектироваться и разрабатываться как mobile-first.

На уровне архитектуры это означает:

- страницы должны быть легкими и не перегруженными;
- фото и видео не должны ломать загрузку на мобильном интернете;
- навигация должна работать на телефонах, планшетах и компьютерах;
- контактные действия должны быть удобны на мобильных устройствах;
- контент должен оставаться читаемым на разных размерах экранов.

Точные визуальные правила и поведение интерфейса должны быть описаны позже в visual rules / skills.

## 11. Что не входит в архитектуру первой версии

В первую версию архитектуры не входят:

- Supabase;
- база данных;
- административная панель;
- авторизация;
- личный кабинет;
- роли пользователей;
- формы сбора личной информации;
- сохранение заявок;
- CRM-логика;
- онлайн-оплата;
- онлайн-бронирование;
- автоматический пересчет валют;
- загрузка медиа пользователями или владельцем через интерфейс сайта;
- автоматическая публикация отзывов.

Эти возможности могут быть добавлены позже только через отдельные спецификации.

## 12. Основа для будущего расширения

Хотя первая версия должна быть простой, архитектура не должна закрывать путь к будущему развитию.

В будущем проект может быть расширен:

- подключением Supabase;
- административной панелью;
- хранением объектов и медиа в backend;
- управлением отзывами;
- управлением контактами;
- расширенной SEO-структурой;
- аналитикой;
- дополнительными разделами сайта.

Эти будущие возможности не должны усложнять первую версию, но текущие технические решения должны быть достаточно понятными, чтобы их можно было развивать без полной переделки проекта.

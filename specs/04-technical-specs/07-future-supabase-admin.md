# Technical spec: будущая админка и Supabase

## 1. Назначение документа

Этот документ описывает будущий технический этап с административной панелью и Supabase.

Админка и Supabase не входят в первую публичную версию сайта Крим. Первая версия должна работать как публичный сайт с заранее подготовленным контентом в файлах проекта.

Документ нужен для того, чтобы первая версия не была перегружена backend-логикой, но при этом сохраняла понятное направление для будущего расширения.

## 2. Статус для первой версии

В первой версии не нужно реализовывать:

- Supabase;
- базу данных;
- Supabase Storage;
- административную панель;
- авторизацию администратора;
- роли пользователей;
- загрузку фото и видео через интерфейс;
- редактирование объектов через сайт;
- управление отзывами через сайт;
- хранение обращений;
- CRM-логику.

Контент первой версии должен добавляться вручную через файлы проекта, после чего выполняются commit, push и deploy.

## 3. Когда может понадобиться админка

Админка может понадобиться после первой публичной версии, если компания подтвердит, что ей нужно самостоятельно управлять контентом.

Причины для будущей админки:

- владелец или менеджер хочет сам добавлять объекты;
- нужно часто менять статусы объектов;
- нужно загружать и удалять фото;
- нужно загружать и удалять короткие видео;
- нужно менять описания объектов;
- нужно менять цену;
- нужно добавлять или скрывать отзывы;
- нужно менять контакты;
- нужно управлять текстами сайта без разработчика.

Если изменения происходят редко, ручное обновление через файлы проекта может оставаться достаточным.

## 4. Возможная роль Supabase

Supabase может быть использован на будущем этапе как backend для сайта и админки.

Потенциальные задачи Supabase:

- хранение объектов;
- хранение характеристик объектов;
- хранение статусов;
- хранение мультиязычных текстов;
- хранение контактов;
- хранение отзывов;
- хранение данных о медиа;
- хранение пользователей админки;
- авторизация администратора;
- хранение файлов через Supabase Storage, если это будет выбрано;
- права доступа для админки.

Подключение Supabase должно выполняться только после отдельной спецификации и плана.

## 5. Что может управляться через будущую админку

В будущей админке можно предусмотреть управление:

- объектами;
- статусами объектов;
- описаниями объектов;
- характеристиками объектов;
- ценой в USD;
- фотографиями;
- короткими видео;
- контактами;
- реальными отзывами;
- доверительными блоками;
- текстами страниц;
- языковыми версиями контента.

Каждая из этих возможностей должна быть отдельно описана перед реализацией. Нельзя просто добавить админку как общий большой модуль без уточнения сценариев.

## 6. Объекты в будущей базе данных

Если Supabase будет подключен, объекты могут храниться в базе данных.

Для объекта нужно будет предусмотреть:

- идентификатор;
- slug;
- статус;
- класс объекта;
- тип объекта;
- площадь дома;
- площадь участка;
- количество комнат;
- количество санузлов;
- локацию;
- цену в USD;
- признаки публикации;
- порядок отображения;
- мультиязычные описания;
- связь с фото и видео.

Статусы должны оставаться согласованными с текущими specs:

- строится;
- доступен;
- продан.

Добавление новых статусов требует обновления спецификаций.

## 7. Медиа в будущей админке

Если будет добавлена загрузка медиа через админку, нужно будет отдельно описать:

- где хранятся файлы;
- кто может загружать файлы;
- кто может удалять файлы;
- какие форматы разрешены;
- какие размеры и ограничения веса применяются;
- как создаются обложки видео;
- как медиа связывается с объектом;
- как выбирается основное фото объекта;
- как скрываются временные или неподходящие материалы;
- как не допустить публикацию стоковых материалов как реальных работ компании.

Supabase Storage может быть рассмотрен как вариант, но не должен подключаться без отдельного решения.

## 8. Отзывы в будущей админке

Отзывы требуют осторожной логики.

Если отзывы будут управляться через админку, нужно предусмотреть:

- добавление только реальных отзывов;
- возможность скрыть отзыв;
- признак разрешения к публикации;
- язык оригинала;
- перевод, если он используется;
- связь с объектом или типом работы, если это доступно;
- запрет на публикацию временных заглушек как реальных отзывов.

Фальшивые отзывы не должны становиться частью публичного сайта.

## 9. Контакты в будущей админке

В будущей версии админка может управлять контактами.

Можно предусмотреть:

- номер телефона;
- WhatsApp;
- Viber;
- подписи и поясняющие тексты;
- включение или отключение отдельного канала связи.

Email не входит в первую версию и не должен появляться автоматически без обновления спецификаций.

Формы заявки также не должны добавляться только из-за появления админки. Для них нужна отдельная спецификация.

## 10. Авторизация и права доступа

Если появится админка, для нее нужна авторизация.

Нужно будет отдельно описать:

- кто имеет доступ к админке;
- какие роли нужны;
- кто может добавлять объекты;
- кто может менять цены;
- кто может публиковать или скрывать материалы;
- кто может менять контакты;
- как защищается доступ к админке.

В первой версии эти вопросы не реализуются.

## 11. Миграция с файлов на Supabase

Если проект перейдет с файлового контента на Supabase, нужна отдельная миграция.

Перед миграцией нужно будет:

- описать структуру таблиц;
- описать связи объектов, медиа, отзывов и переводов;
- перенести текущий контент;
- проверить все публичные страницы;
- сохранить URL объектов;
- не сломать SEO;
- убедиться, что украинская и русская версии продолжают работать;
- проверить контакты и статусы объектов.

Миграция не должна выполняться как быстрый перенос без плана.

## 12. Что нельзя делать при будущем расширении

При добавлении Supabase и админки нельзя:

- ломать уже утвержденные публичные сценарии;
- скрывать цену за формой или звонком;
- добавлять сбор личной информации без отдельной спецификации;
- публиковать временные отзывы как реальные;
- превращать сайт в сложную CRM без отдельного решения;
- усложнять первую версию заранее;
- менять URL объектов без необходимости;
- добавлять новые статусы объектов без обновления specs;
- смешивать украинский и русский контент в одном интерфейсе.

Будущий backend должен расширять сайт, а не менять его утвержденный смысл.

## 13. Когда возвращаться к этому документу

К этому документу нужно вернуться после первой публичной версии, если компания решит, что ручного обновления контента через файлы проекта уже недостаточно.

Перед началом работ по админке нужно будет подготовить новые спецификации:

- user stories для владельца или менеджера;
- work plan по Supabase;
- technical spec базы данных;
- technical spec авторизации;
- technical spec загрузки фото и видео;
- technical spec управления объектами;
- technical spec управления отзывами;
- technical spec безопасности и прав доступа.

## 14. Итоговое правило

Supabase и админка являются будущим этапом, а не частью первой версии.

Первая версия должна оставаться простой: публичный сайт, подготовленный контент, реальные фото и видео, страницы объектов, мультиязычность, цена в USD и быстрые контакты через телефон, WhatsApp и Viber.

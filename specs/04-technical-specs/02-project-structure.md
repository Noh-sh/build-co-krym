# Technical spec: структура проекта Next.js

## 1. Назначение документа

Этот документ описывает техническую структуру проекта Next.js для первой версии сайта Крим.

Структура проекта должна поддерживать публичный сайт, страницы объектов, фото и видео, контакты, мультиязычность, отображение цены в USD и базовую SEO-подготовку.

Документ не описывает визуальный стиль, точный дизайн компонентов, структуру данных объектов, форматы медиа или правила SEO. Эти темы должны быть описаны в отдельных technical specs.

## 2. Общий принцип структуры

Проект должен быть организован так, чтобы его было легко читать, поддерживать и расширять.

Основной принцип:

- страницы отвечают за маршруты;
- компоненты отвечают за переиспользуемые части интерфейса;
- данные сайта хранятся отдельно от компонентов;
- переводы хранятся отдельно от бизнес-данных;
- медиа хранятся в понятной структуре;
- технические утилиты не смешиваются со страницами;
- будущая админка не добавляется в структуру первой версии.

Структура должна быть понятной для человека, который впервые открывает проект.

## 3. Базовая структура проекта

Для первой версии нужно использовать понятную структуру Next.js проекта.

Рекомендуемая структура:

```txt
src/
  app/
  components/
  content/
  i18n/
  lib/
  styles/
public/
  images/
  videos/
specs/
```

Если при создании проекта будет выбран другой технический шаблон Next.js, структура может быть уточнена, но общий принцип разделения страниц, компонентов, контента, переводов, медиа и утилит должен сохраниться.

## 4. Папка `src/app`

Папка `src/app` должна отвечать за маршруты и страницы сайта.

В ней должны находиться:

- главная страница;
- страница списка проектов и домов;
- страницы отдельных объектов;
- страница контактов;
- страницы или разделы для выполненных работ, фото, видео, отзывов и информации о компании, если они будут реализованы как отдельные маршруты;
- технические файлы Next.js для layout, metadata и обработки отсутствующих страниц.

Страницы не должны превращаться в большие файлы со всей логикой и всем интерфейсом. Повторяемые блоки нужно выносить в компоненты.

Точная схема маршрутов должна быть описана в technical spec по маршрутам и SEO.

## 5. Папка `src/components`

Папка `src/components` должна хранить переиспользуемые части интерфейса.

В ней можно предусмотреть группы компонентов:

```txt
components/
  layout/
  navigation/
  objects/
  media/
  contacts/
  language/
  trust/
  ui/
```

Назначение групп:

- `layout` — общая оболочка страниц, header, footer, основные каркасы;
- `navigation` — навигация по сайту;
- `objects` — карточки объектов, статусы, характеристики, блоки объектов;
- `media` — галереи, видео-блоки, медиа-превью;
- `contacts` — кнопки звонка, WhatsApp, Viber и контактные блоки;
- `language` — переключатель языка и связанные элементы;
- `trust` — отзывы и блоки доверия;
- `ui` — простые базовые элементы интерфейса, если они действительно переиспользуются.

Компоненты должны быть небольшими и понятными. Не нужно заранее создавать сложную дизайн-систему, если она не требуется первой версии.

## 6. Папка `src/content`

Папка `src/content` должна хранить подготовленный контент первой версии.

В ней должны находиться данные, которые можно менять вручную без изменения логики компонентов:

- объекты;
- тексты страниц;
- контактные данные;
- цены;
- статусы;
- ссылки на фото и видео;
- реальные отзывы, если они доступны;
- доверительные факты о компании.

Пример возможной структуры:

```txt
content/
  objects/
  pages/
  contacts/
  reviews/
  company/
```

Формат хранения данных должен быть описан отдельно в technical spec по контенту и данным.

## 7. Папка `src/i18n`

Папка `src/i18n` должна хранить технические настройки мультиязычности.

В ней можно предусмотреть:

- список поддерживаемых языков;
- язык по умолчанию;
- словари интерфейсных текстов;
- helper-функции для получения нужной языковой версии;
- правила fallback-поведения при неполном переводе.

Контент объектов может храниться в `src/content`, но должен быть подготовлен с учетом двух языковых версий.

Точная схема мультиязычности должна быть описана в technical spec по i18n.

## 8. Папка `src/lib`

Папка `src/lib` должна хранить технические утилиты и вспомогательную логику.

В ней можно предусмотреть:

- функции для получения объектов;
- функции для фильтрации или группировки объектов по статусу;
- функции для форматирования цены в USD;
- функции для подготовки SEO-данных;
- функции для работы с контактными ссылками;
- общие типы данных, если будет использоваться TypeScript.

В `src/lib` не должны попадать визуальные компоненты и тексты страниц.

## 9. Папка `src/styles`

Папка `src/styles` должна хранить глобальные стили, если они требуются выбранной структуре проекта.

Стили должны поддерживать:

- mobile-first подход;
- адаптацию под телефоны, планшеты и компьютеры;
- читаемость текста;
- удобное отображение медиа;
- стабильную работу интерфейса на разных размерах экранов.

Подробные визуальные правила будут описаны позже в разделе visual rules / skills.

## 10. Папка `public`

Папка `public` должна хранить публичные статические файлы.

В первой версии там можно предусмотреть:

```txt
public/
  images/
    objects/
    company/
    trust/
  videos/
    objects/
    process/
```

Медиа должны быть организованы так, чтобы было понятно, к какому объекту или разделу они относятся.

Если на следующем этапе будет выбран внешний storage для части медиа, это должно быть отдельно описано в technical spec по фото и видео. До такого решения базовый вариант — хранение подготовленных медиа в проекте.

## 11. Папка `specs`

Папка `specs` остается местом для всей проектной документации.

Код приложения не должен смешиваться со спецификациями.

Документация должна продолжать развиваться по правилу:

```txt
Сначала SPEC → потом PLAN → потом CODE
```

## 12. Что не нужно добавлять в первую версию структуры

В первой версии не нужно заранее добавлять:

- папки для административной панели;
- Supabase-клиент;
- API для заявок;
- backend-роуты для сохранения данных;
- папки для ролей пользователей;
- CRM-модули;
- загрузчики файлов через интерфейс сайта;
- сложную систему управления переводами;
- структуру для онлайн-оплаты или бронирования.

Эти части появятся только после отдельных спецификаций.

## 13. Требования к понятности структуры

Структура проекта должна быть лаконичной.

Если файл или папка не нужны первой версии, их не нужно создавать заранее.

Название папки или файла должно ясно объяснять назначение. Человек, который впервые открывает проект, должен быстро понять:

- где находятся страницы;
- где находятся компоненты;
- где находятся данные;
- где находятся переводы;
- где находятся фото и видео;
- где находятся технические утилиты;
- где лежат спецификации.
